# fort add — a chart's fort-side tree, from its contract

```
fort add <fort> <oci-ref> (--version X | --follow-pr N | --follow-main) [--name app]
         [--hostname fqdn] [--http service:port] [--without type,...]
         [--chart-dir path] [--write]
```

`add` turns a chart into everything a fort needs to run it: the app's
own directory (source, release, route, monitoring, the seeding
contract), the gateway listener and certificate for its hostname, and
the provider instances it requires — a postgres tenant, a valkey ACL
user — created on first need under `forts/`, the one directory and the
one namespace every provider the fort runs shares (deployments#671), and
registered on every need after. It
reads one thing from the chart: the `forts.contract.yaml` it ships,
the chart author's declaration of what the workload needs
([fort configuration contracts](fort-configuration-contracts.md)). What
that turns into on the cluster is [`docs/flux/workloads.md`](../flux/workloads.md).

## Conventions, not flags

| | default | override |
|---|---|---|
| app, namespace, release, dir | the chart's name | `--name` |
| the Secret the chart consumes | `<app>-env` in namespace `<app>`, when the contract declares keys at all | the contract's `secret.values` names the values path |
| hostname | `<app>.<fort>.<zone>` — zone = the manifest's `[dns] zone` on a cloud fort, `lofi` in the lab | `--hostname` |
| issuer | `letsencrypt` on a cloud fort, `step-ca` in the lab | — |
| version | `--version X` pins a tag; `--follow-pr N` follows a PR's preview charts; `--follow-main` follows main's | `--chart-dir` reads a local chart (tests, chart authors) |
| optional providers | provisioned — the out-of-the-box result is the full topology | `--without valkey` drops an *optional* requirement; a required one is refused |
| the Service the fleet routes to | the contract's `http` block | `--http service:port`, for a chart that ships no contract; refused against a contract that declares `http` |

`add` is refused on a fort that is not a flux cluster, on a fort without
an apps root (scaffold first), and on an app dir that already exists —
**`fort add` never overwrites**; remove the dir or refine in place.

## What it renders

The captured report for symbology on a fresh cloud fort:


Three marks, the same ones PR descriptions and the golden tests use: `●`
new, `○` an existing file gaining lines (never a rewrite — appends are
text-level so comments survive), `◆` generated by [`seed`](seed.md),
never by hand.

**The app dir.** `repository.yaml` is an `OCIRepository` in `flux-system`
with the lab CA supplied explicitly (source-controller pods do not
inherit the node's trust the way containerd does), hence the local
`step-ca-root.pem` copy and the `<app>-oci-ca` secretGenerator in the
kustomization. `release.yaml` is the `HelmRelease`: chart by reference,
**install and upgrade remediation retries `-1`** — the first install
races its providers and a preview pin races its images, and a release
must never park failed waiting for an ops nudge (add renders `-1` for
every app; a release whose upgrade migrates a schema forward overrides it
by hand, [contracts](fort-configuration-contracts.md)) — and `values` filled
from the contract's `wire:` map by convention (below). `route.yaml` is
the `HTTPRoute` from the hostname to the contract's `http.service:port`,
attached to the gateway listener named for the app; `monitoring.yaml` a
`PodMonitor` when the contract declares `metrics`. `secrets.sops.yaml` is
listed in the kustomization before it exists: `kustomize build` fails
until seed creates it, the repo's pre-merge guard. `forts.contract.yaml`
is the fort-side **full form** of the chart's contract — every key with
its source, the `external` ones carried through for you to point at a
source the seeder can read.

**The secret-less app.** A contract that declares no `secret.keys`
declares no Secret, and add renders none of the machinery for it: no
`secrets.sops.yaml` (neither the file nor the kustomization entry that
guards it), no fort-side `forts.contract.yaml`, and no `existingSecret`
in the HelmRelease values — a `values:` block that would otherwise be
empty is left out altogether. The report says so where the seed line
normally goes:

```
flux/apps/sfi-x/   (chart 0.1.0)
● gateway/
  …
○ kustomization.yaml             + gateway, moment-tally-website
● moment-tally-website/
  ● kustomization.yaml
  ● namespace.yaml
  ● release.yaml                 wire: none; retry forever — refine replicas/env in place
  ● repository.yaml              OCIRepository oci://gitea.zen.lofi/sfi/moment-tally-website, tag 0.1.0
  ● route.yaml                   HTTPRoute moment-tally-website.sfi-x.lofi → moment-tally-website:3000
  ● step-ca-root.pem             copy of flux/infrastructure/configs/step-ca-root.pem

staged. nothing to seed: the chart contract declares no keys, so the app has no Secret.
then: review, commit, PR — flux applies on merge.
```

moment-tally-website is the case: a stateless SSR site whose only
runtime config is embedded in every served page, so it is plain values.
`fort seed` plans no Secret for such a dir and `fort check` demands
none. The day a genuinely secret env var appears, the chart adds
`secret.keys` and the next `fort add` — or a hand-written
`secrets.sops.yaml` plus its kustomization entry — restores the full
shape.

**The chart that ships no contract.** A chart declares its needs in the
`forts.contract.yaml` it ships, and a chart that ships none declares
nothing. `add` plans from that: no providers, no Secret, no route, and
the app dir alone — `namespace.yaml`, `repository.yaml`,
`release.yaml`, `step-ca-root.pem` and the kustomization. The report
says what the absence costs, because nothing else can:

```
flux/apps/sfi-x/   (chart 0.0.0-pr.48.108.g42d6bce)
○ kustomization.yaml             + moment-tally-website
● moment-tally-website/
  ● kustomization.yaml
  ● namespace.yaml
  ● release.yaml                 wire: none; retry forever — refine replicas/env in place
  ● repository.yaml              OCIRepository oci://gitea.zen.lofi/sfi/moment-tally-website, tag 0.0.0-pr.48.108.g42d6bce
  ● step-ca-root.pem             copy of flux/infrastructure/configs/step-ca-root.pem

note: the chart ships no forts.contract.yaml. This app gets no key gate: `fort check`
      cannot see a chart bump that starts to need a key. The chart adopts the
      gate when it ships the file — docs/fort-configuration-contracts.md.
note: nothing declares an http service, so this app has no listener, no
      certificate and no route. It is reachable on the mesh and the LAN only.
      Add ingress with `fort add … --http <service>:<port>`.

staged. nothing to seed: the chart ships no contract, so the app has no Secret.
then: review, commit, PR — flux applies on merge.
```

`--http <service>:<port>` gives such an app its ingress: the gateway
listener, the certificate and the route, exactly as a contract's `http`
block produces them. Type what the chart exposes — for
moment-tally-website that is `--http moment-tally-website:3000`. The
contract wins wherever there is one: `--http` against a chart that
declares `http` is refused, and the error names what the chart
declares. A malformed contract is still an error too; absent and broken
are different facts.

**The gateway.** One `Gateway homelab` in `traefik` per fort with a
single http listener, a catch-all `http→https` 301 (cert-manager's
challenge routes match an exact path and take precedence), and per app a
JSON6902 patch that appends an https listener with `tls.certificateRefs
<app>-tls`, plus the `Certificate` that fills it. JSON6902 is the one
place strategic merge cannot serve: kustomize has no merge key for a
CRD's listener list. On a lab fort the `step-ca` ClusterIssuer is copied
beside the gateway — per cluster, not shared, because a cloud cluster
can never reach `step-ca.lofi` and a `Ready=False` issuer wedged web3's
infrastructure health checks for hours.

**Providers.** Every provider the fort runs lives under one directory,
`forts/`, in the one namespace that directory owns, `forts`
(deployments#671): `kubectl get pods -n forts` is the set, with no label
and no filter. The first provider need renders `forts/namespace.yaml`
and `forts/kustomization.yaml` with the root kustomization's one `forts`
entry; a later need of another type appends one line to the forts
kustomization. The instances keep the names of what they are — the
CNPG Cluster `postgres`, the HelmReleases `valkey` and `rustfs` — and
carry no namespace of their own (kustomize refuses two Namespace
documents with the same id). Each is rendered on first need from
`templates/add/{postgres,valkey,rustfs}` into `forts/<name>/`, then
registered per tenant. The postgres instance's archive follows the
manifest's `[backups] profile`: `production` renders the barman-cloud
plugin with an `ObjectStore` on B2 (`s3://sfi-db-physical-backups/<fort>`),
the nightly `ScheduledBackup`, and a `secrets-backup` contract entry whose
two keys are `external` — the fort's own `sfi-db-physical-<fort>` key,
minted by `fort b2-key db-physical <fort> --write` and set with
`fort seed <fort> postgres --set`. `lab` (and `none`) render **no archive**
and say so in `cluster.yaml`: no lab fort ships barman anywhere, and a
cluster that silently archives into nothing is the failure the backups
design refuses ([`docs/infra/backups.md`](../infra/backups.md)). Tenants
are then registered the same way on either: a `Database` CR, a JSON6902 patch adding the
role to `spec.managed.roles` (kept an empty list in the template so the
patch has a target), and the tenant's credentials Secret in the
provider's own contract; for valkey an ACL user patch and a key in
`valkey-users`. The valkey `db` index is the count of existing
`acl-*.yaml`. For s3 (#326) the first need renders `forts/rustfs/` — luxor's
instance without the route, its metrics bridge and `RustfsDown` rule, the
bucket Job, the `rustfs-iam` CronJob, and a contract with the root pair
and the identity list — and every tenant is `policies/<app>.json`
(get/put/list/delete on bucket `<app>`, nothing else), a `rc bucket
create` line, a `files:` entry in the policies generator and a key
`<app>` in `rustfs-users`. The identity's name is its access key and its
bucket. All three providers are one instance per fort by construction —
the monolith is the decision — and none is ever touched again by add
once its tenant is registered (`○ untouched — tenant already registered`).
Details in [`docs/infra/providers.md`](../infra/providers.md).

## What the contract wires

The chart declares its needs; the fort fills the values by convention:

| provider | output | value |
|---|---|---|
| postgres | `host` / `port` / `name` / `user` | `postgres-rw.forts.svc.cluster.local` / `5432` / `<app>` / `<app>` |
| postgres | `password` | secret-typed: a `sops:` ref into `../forts/postgres/secrets-<app>.sops.yaml`, only reachable from `secret.keys` templates |
| valkey | `host` / `port` / `db` / `user` | `valkey.forts.svc.cluster.local` / `6379` / next free index / `<app>` |
| valkey | `password` | secret-typed, from `../forts/valkey/secrets.sops.yaml` key `<app>` |
| s3 | `endpoint` / `bucket` / `accessKey` | `http://rustfs-svc.forts.svc.cluster.local:9000` / `<app>` / `<app>` |
| s3 | `secretKey` | secret-typed, from `../forts/rustfs/users.sops.yaml` key `<app>` |

`uri` outputs are deliberately not composed. Non-secret outputs go into
HelmRelease values through `wire:`; secret-typed ones may only feed
Secret keys. Endpoints are values, passwords are secret-borne — a values
change rolls pods, a Secret change does not.

## Following a PR

`--follow-pr N` pins `ref.semver: ">=0.0.0-0"` with a filter on
`0.0.0-pr.N.*`: every commit of the PR publishes an immutable prerelease
chart whose `appVersion` is that commit's sha, `0.0.0-` sorts below every
release so no renovate bump can ever pick one up, and the `OCIRepository`
status records exactly which revision runs. **The moment the PR merges
and is tagged, move the pin to the tag**: the registry's cleanup rule
deletes preview packages by age, and a fort left on the filter goes
`FetchFailed` (the drill fort, 2026-09-14) — the stored artifact keeps
serving, but nothing new ever arrives.

## Following main

`--follow-main` is the same mechanism on the other preview line:
`0.0.0-main.<run>.g<sha>`, published by the chart repo's `chart-preview`
workflow on every push to main. The filter is `^0\.0\.0-main\.` and the
file names no version — every merge in the chart repo reaches the fort
on the next reconcile, with no commit here.

This is the **staging** pin (#456). A tag holds still, a PR filter
points at one unmerged branch, and a staging fort wants neither: it
runs what main says, continuously. `sfi-stage-d95cc36` follows
moment-tally-website this way.

Three things the pin asks of the chart repo and of a fort that takes it:

- **The chart repo must publish the main line.** A chart whose
  `chart-preview` workflow runs on `pull_request` only has no
  `0.0.0-main.*` package, and `add` (and later `fort check`) says so:
  `Could not locate a version matching provided version string`.
- **The registry cleanup rule must reach the main line and keep it.**
  The rule deletes `0.0.0-` packages by age. A retention window shorter
  than the gap between merges to main empties the filter, and the fort
  goes `FetchFailed` — the same failure a fort left on a merged PR's
  filter reaches.
- **Nothing pins the fort to a reviewed artifact.** Main is the review.
  A fort that must hold still — production — pins a tag.

Renovate is unaffected either way: it never sees a `0.0.0-` prerelease.

## After `--write`, by hand

The report ends with the two things add cannot know:

```
next: seed the ◆ files (dependency order is derived):
  fort seed sfi-x --write
external keys — absent from the Secret until set (sops set, or a sops/env ref in the contract):
  STRIPE_SECRET_KEY   Stripe → API keys
  ACCESS_KEY_ID       postgres: `fort b2-key db-physical sfi-x --write`, then `fort seed sfi-x postgres --set ACCESS_KEY_ID --write`
  ACCESS_SECRET_KEY   postgres: the same mint; `fort seed sfi-x postgres --set ACCESS_SECRET_KEY --write`
then: review, commit, PR — flux applies on merge.
```

- **Externals**: replace each `{external: …}` in the fort-side contract
  with a `sops:` ref the seeder can read (a sibling fort's Secret is the
  precedent for a clone), or `fort seed <fort> <app> --set KEY` from
  stdin after seeding.
- **Non-secret values** are refinements every time: replicas for the
  node shape, `fullnameOverride` where the chart's `http.service` assumes
  it, the app's public URL (`BETTER_AUTH_URL`, `PUBLIC_*`) as `env:` in
  values — never in the Secret.
- **The archive key** on a production fort is the one external `add`
  lists that no chart asked for: mint it, seed it, and only then merge —
  the `ObjectStore` with an empty Secret is a cluster that archives
  nothing while its manifest says `production`.
- **A fort provisioned from a backup** flips the greenfield `postgres` cluster
  to `bootstrap.recovery` by hand before the first apply; initdb and
  recovery run at creation only, so it is a re-provision, never a live edit.
  The barman plugin stores a cluster under its `serverName`, so a fort
  provisioned from a fort that predates the forts namespace recovers from
  `serverName: sites-db-v1` in the `externalClusters` block. Stagger the
  nightly backup hour across forts while you are there.
- **Alert rules are policy**: the PodMonitor is rendered, the rules that
  page someone are added by hand.

Then `fort check <fort>`, PR, merge; flux applies.
