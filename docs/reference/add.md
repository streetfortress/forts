# fort add — a contract in, an inventory out

```
fort add <fort> <oci-ref> (--version X | --follow-pr N | --follow-main) [--name app]
         [--hostname fqdn] [--http service:port] [--chart-dir path] [--dry-run]
```

`add` turns a chart into the directory a flux cluster needs to run it:
the `OCIRepository` that pins the chart, the `HelmRelease`, the entry
in the fort's apps kustomization, the [inventory](inventory.md) of the
Secret the chart consumes, and — when the chart's contract (or
`--http`) names a Service — the gateway listener, the certificate and
the `HTTPRoute` for its hostname. It reads one thing from the chart:
the `forts.contract.yaml` it ships, the chart author's declaration of
what the workload needs ([contracts](contracts.md)). **`add` takes a
contract in and writes an inventory out.**

The core renders what its own init templates install: the gateway stack
(traefik, cert-manager, the Gateway API CRDs) and the inventory that
[`seed`](seed.md) executes. A platform service the contract
`requires` — a database, a cache, a bucket — is not the core's: a layer
renders it after `add`, in the same tree (sfi/fort-layers,
[layers](layers.md)). `add` names what it leaves to the layer and
renders none of it.

## Conventions, not flags

| | default | override |
|---|---|---|
| app, namespace, release, dir | the chart's name | `--name` |
| the Secret the chart consumes | `<app>-env` in namespace `<app>`, when the contract declares keys at all | the contract's `secret.values` names the values path |
| hostname | `<app>.<fort>.<zone>` — zone = the manifest's `[dns] zone` where the fort has one, else the estate's mesh zone (`estate.toml` `zone`, else `<estate>.mesh`; [mesh](mesh.md)) | `--hostname` |
| issuer | `letsencrypt`, the ClusterIssuer the shared layer carries when `estate.toml` names an `[acme]` email ([init](init.md)) | — |
| version | `--version X` pins a tag; `--follow-pr N` follows a PR's preview charts; `--follow-main` follows main's | `--chart-dir` reads a local chart (tests, chart authors) |
| the Service the fleet routes to | the contract's `http` block | `--http service:port`, for a chart that ships no contract; refused against a contract that declares `http` |
| the registry's CA | `nixos/certs/ca-root.pem` when the estate carries one: copied beside the app and handed to the `OCIRepository` as `certSecretRef` | — (absent, the system roots serve) |

`add` is refused on a fort without an apps root (scaffold first) and on
an app dir that already exists — **`fort add` never overwrites**;
remove the dir or refine in place. A chart is pulled with `helm` at
the pin, so the registry must be reachable; `--chart-dir` reads a
local chart instead.

## What it renders

The report for a chart with every block the core reads, on a cloud
fort whose estate carries a CA:

```
flux/apps/cloud-fort/   (chart 0.3.0)
● gateway/
  ● certificate-sfi-website.yaml letsencrypt, sfi-website.cloud-fort.example.cloud
  ● gateway.yaml                 http listener only
  ● kustomization.yaml           patches: listener-sfi-website.yaml
  ● listener-sfi-website.yaml    JSON6902 add /spec/listeners/- (https-sfi-website)
  ● redirect-https.yaml          catch-all http→https 301
○ kustomization.yaml             + gateway, sfi-website
● sfi-website/
  ● ca-root.pem                  copy of nixos/certs/ca-root.pem
  ● forts.inventory.yaml               the inventory: 2 keys and their sources
  ● kustomization.yaml
  ● monitoring.yaml              PodMonitor sfi-website-ui (rules are policy: by hand)
  ● namespace.yaml
  ● release.yaml                 values: sfi-website-env as the Secret; retry forever — refine replicas/env in place
  ● repository.yaml              OCIRepository oci://gitea.zen.lofi/sfi/sfi-website, tag 0.3.0
  ● route.yaml                   HTTPRoute sfi-website.cloud-fort.example.cloud → sfi-website-ui:3000
  ◆ secrets.sops.yaml            seeded

staged. next: seed the ◆ files:
  fort seed cloud-fort
external keys — absent from the Secret until set (fort seed --set, or a sops/env ref in the inventory):
  RESEND_API_KEY           Resend → API keys (re_) (optional)
then: review, commit, PR — flux applies on merge.
```

Three marks, the same ones PR descriptions and the golden tests use: `●`
new, `○` an existing file gaining lines (never a rewrite — appends are
text-level so comments survive), `◆` generated by [`seed`](seed.md),
never by hand.

**The app dir.** `repository.yaml` is an `OCIRepository` in
`flux-system`. `release.yaml` is the `HelmRelease`: chart by reference,
**install and upgrade remediation retries `-1`** — the first install
races its providers and a preview pin races its images, and a release
must never park failed waiting for an ops nudge (a release whose upgrade
migrates a schema forward overrides it by hand,
[contracts](contracts.md)) — and `values` carrying the Secret's name at
the contract's `secret.values` path. `route.yaml` is the `HTTPRoute`
from the hostname to the contract's `http.service:port`, attached to
the gateway listener named for the app; `monitoring.yaml` a
`PodMonitor` when the contract declares `metrics`, which the edge
Prometheus of every cluster scrapes. `secrets.sops.yaml` is listed in
the kustomization before it exists: `kustomize build` fails until seed
creates it, the repo's pre-merge guard. `forts.inventory.yaml` records every
key of that Secret with its source — the `external` ones carried
through for you to point at a source the seeder can read.

**The secret-less app.** A contract that declares no `secret.keys`
declares no Secret, and add renders none of the machinery for it: no
`secrets.sops.yaml` (neither the file nor the kustomization entry that
guards it), no `forts.inventory.yaml`, and no `values:` block
in the HelmRelease. `fort seed` plans no Secret for such a dir and
`fort check` demands none.

**The chart that ships no contract.** A chart declares its needs in
the `forts.contract.yaml` it ships, and a chart that ships none
declares nothing. `add` plans from that: no Secret, no route, and the
app dir alone. The report says what the absence costs, because nothing
else can:

```
note: the chart ships no forts.contract.yaml. This app gets no key gate: `fort check`
      cannot see a chart bump that starts to need a key. The chart adopts the
      gate when it ships the file — docs/reference/contracts.md.
note: nothing declares an http service, so this app has no listener, no
      certificate and no route. It is reachable on the mesh and the LAN only.
      Add ingress with `fort add … --http <service>:<port>`.
```

`--http <service>:<port>` gives such an app its ingress: the gateway
listener, the certificate and the route, exactly as a contract's `http`
block produces them. The contract wins wherever there is one: `--http`
against a chart that declares `http` is refused, and the error names
what the chart declares. A malformed contract is still an error too;
absent and broken are different facts.

**The gateway.** One `Gateway homelab` in `traefik` per fort with a
single http listener, a catch-all `http→https` 301 (cert-manager's
challenge routes match an exact path and take precedence), and per app
a JSON6902 patch that appends an https listener with
`tls.certificateRefs <app>-tls`, plus the `Certificate` that fills it.
JSON6902 is the one place strategic merge cannot serve: kustomize has
no merge key for a CRD's listener list. The first app with an http need
renders the directory; the next appends to its kustomization — the
certificate as a resource, the listener inside the `patches:` list,
never at the end of the file. The certificate names the estate's
`letsencrypt` ClusterIssuer, whatever directory it speaks to; an
estate whose `estate.toml` names no `[acme]` email carries none, and
the report says the certificate waits.

**The chart that requires a platform service.** A contract's
`requires` block names what the chart consumes — `postgres.db`,
`valkey.cache` — and the core renders none of it. `add` still renders
the app dir: the route, the release, and the inventory with any
`template` key that composes a provider output (`${postgres.db.password}`)
written **verbatim**. The report names both halves a layer owes:

```
note: the chart requires postgres.db — a platform service the core does not render.
      A layer renders it and wires it into release.yaml (sfi/fort-layers);
      until then the release waits on it.
note: DATABASE_URL (postgres.db) composes provider outputs the core does not resolve. The
      layer rewrites the key to a source in forts.inventory.yaml; `fort seed` waits for it.
```

The layer's `add` runs after the core's: it renders the instance and
the tenant, wires the instance's endpoints into `release.yaml`, and
rewrites each template key of the inventory to a `sops:` ref into the
tenant's Secret. Then `fort seed` seeds both. Until the layer
runs, `fort seed` refuses that key by name and `fort check` stays red
on the absent Secret — the PR is not mergeable, which is the gate
working.

## Following a PR

`--follow-pr N` pins `ref.semver: ">=0.0.0-0"` with a filter on
`0.0.0-pr.N.*`: every commit of the PR publishes an immutable
prerelease chart whose `appVersion` is that commit's sha, `0.0.0-`
sorts below every release so no renovate bump can ever pick one up,
and the `OCIRepository` status records exactly which revision runs.
**The moment the PR merges and is tagged, move the pin to the tag**: a
registry's cleanup rule deletes preview packages by age, and a fort
left on the filter goes `FetchFailed` — the stored artifact keeps
serving, but nothing new ever arrives.

## Following main

`--follow-main` is the same mechanism on the other preview line:
`0.0.0-main.<run>.g<sha>`, published by the chart repo's preview
workflow on every push to main. The filter is `^0\.0\.0-main\.` and
the file names no version — every merge in the chart repo reaches the
fort on the next reconcile, with no commit here. This is the staging
pin: a tag holds still, a PR filter points at one unmerged branch, and
a staging fort wants neither. Three things it asks: the chart repo
must publish the main line; the registry's cleanup rule must keep it
for longer than the gap between merges; and nothing pins the fort to a
reviewed artifact — main is the review. A fort that must hold still
pins a tag.

## After add, by hand

- **Externals**: replace each `{external: …}` in the inventory with a
  `sops:` or `env:` ref the seeder can read (a sibling
  fort's Secret is the precedent for a clone), or `fort seed <fort>
  <app> --set KEY` from stdin after seeding.
- **Non-secret values** are refinements every time: replicas for the
  node shape, `fullnameOverride` where the chart's `http.service`
  assumes it, the app's public URL as `env:` in values — never in the
  Secret.
- **Alert rules are policy**: the PodMonitor is rendered, the rules that
  page someone are added by hand.

Then `fort seed <fort>`, `fort check <fort>`, PR, merge; flux applies.

The inverse is [`fort remove <fort> <app>`](remove.md): the app dir,
its kustomization entry and its gateway half leave; flux prunes the
workload on the merge.
